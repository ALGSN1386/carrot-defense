## §0 摘要（一屏读完）

网页端塔防小游戏，打开即玩，无需安装 / 账号 / 内购。核心是**资源与地形的双重约束**：金币有限、好位置有限，玩家必须判断哪段路值得投资。一局 15 波、约 10 分钟。

**差异化不在于「更好玩」——塔防品类已经饱和——而在于「工程可验证」**：逻辑层与渲染层完全分离，整套玩法可在 Node 中无头跑完，难度曲线是仿真调出来的，而不是拍脑袋定的。✅ 已校验（见 §7.3）。

## §1 问题与机会

### 1.1 用户在什么时刻需要它

> 晚上十点，你在电脑前等一个构建跑完，或者开会前还有八分钟。你想玩点什么，但不想为此安装一个 300MB 的手游、注册账号、看 30 秒广告，也不想在手机上被推送打断。

这个场景的关键约束不是"想玩游戏"，而是**「短、无承诺、立刻开始」**。任何安装步骤都会让人放弃。

### 1.2 现有方案为什么不够

| 现有方案 | 具体失败点 |
|---|---|
| 原版《保卫萝卜》手游 | 需要安装；有内购与体力机制；旧版本已停止更新 |
| Flash 时代的网页塔防 | 需要模拟器；分辨率与性能不可用 |
| Steam / 主机塔防（Kingdom Rush、Bloons TD） | 品质高但需付费 + 安装，与"八分钟"场景冲突 |
| 视频攻略 | 不参与，只观看，不解决"我想玩" |
| 其他网页塔防 | 多数缺少难度校准，要么一局永远赢不了，要么十分钟通关后没有复玩动力 |

**共同缺口**：没有一个能「打开就用、十分钟打完一局、且难度经过验证」的选项。

### 1.3 为什么现在做

- 现代浏览器已具备全部所需能力（Canvas 2D、ES 模块、requestAnimationFrame），无需任何运行时依赖；
- GitHub Pages 提供零成本、零运维的静态托管；
- 作者需要一件能同时证明**玩法设计**与**工程质量**的作品。

## §2 目标

### 2.1 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 从打开链接到可以操作，不超过 2 秒（4G 中端手机） | 首屏 LCP 实测 |
| G2 | 一局完整对局 6–12 分钟，且难度曲线有梯度 | 仿真验证（§7.3）+ 人工试玩 |
| G3 | 玩法逻辑可被自动化验证，不依赖人工目测 | `game.js` 无 DOM/Canvas 依赖，可在 Node 中跑完整对局 |

### 2.2 非目标（明确不做）

- **不做多人 / 排行榜**：需要后端与账号体系，与"零运维"冲突
- **不做付费 / 广告 / 内购**：本产品不是商业项目
- **不做关卡编辑器**：面向玩家的创作工具是另一个产品
- **不做剧情 / 角色养成**：超出"十分钟一局"的容量
- **不做原生 App 打包**：网页已是完整交付形态

### 2.3 反目标（什么算失败，即使技术上跑通了）

- **A1** 玩家第一次打开，不知道"先点卡片再点地面"——技术正常运行，产品失败
- **A2** 无论怎么打都能赢，或者怎么打都赢不了——数值失衡，失去决策价值
- **A3** 手机端需要精确点击才能建塔，误触率高到让人放弃
- **A4** 为了做数据而引入埋点，使产品带上前端产品的隐私负担
- **A5** 代码只能"看"，不能"验"——无法用任何自动化手段证明玩法正确

## §3 用户与任务

### 3.1 两类用户，两种诉求

| 用户 | 真实诉求 | 成功的一刻 |
|---|---|---|
| **玩家**（顺路点进来） | 立刻玩、别教我、别让我卡住 | 三分钟内搞懂规则，一局有输有赢 |
| **评估者**（同行／招聘方） | 60 秒内判断技术水平 | 看懂"逻辑与渲染分离 + 仿真调参"这件事的分量 |

这两类用户的诉求不冲突，且可以同时满足，因此不需要分叉产品线。

### 3.2 核心任务（Jobs to be Done）

> 当我只有十分钟且不想做任何准备工作时，我想要一个能立刻开始、且真的需要动脑的小游戏，这样我能在短时间内获得一次完整的挑战与结束感。

### 3.3 为什么不做用户画像

不做年龄/职业/收入分层。产品只有一个决策依据：**这次会话有多长**。任何不能用"会话时长"解释的用户差异，对本产品的设计没有影响。

## §4 范围与功能需求

### 4.1 版本范围

v1.0 只做**单张地图 + 完整单局循环**。多地图、无尽模式、音效全部推后（§4.3）。

### 4.2 需求清单

优先级定义：**P0 = 缺了就不是这个产品**；P1 = 影响体验但可延后。

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| R1 | P0 | 打开即可玩，无账号、无安装、无引导弹窗 | 冷加载到可点击 ≤ 2s；首屏无任何模态框；不产生任何第三方网络请求 |
| R2 | P0 | 建塔：选卡 → 点空地 → 扣费建造 | 金币不足时按钮置灰且给出差额提示；路面/装饰格不可建造（红色高亮）；已占用格不可重复建造 |
| R3 | P0 | 塔可升 3 级、可拆除 | 升级后伤害 ×1.65、射程 +18、间隔 ×0.88（每级，复合）；满级后按钮显示"已满级"；拆除返还累计投入的 60% 且立即到账 |
| R4 | P0 | 15 波怪物，20 点生命，生命归零失败 | 第 5/10/15 波为首领波；每波生命按 `1 + 0.15 × (波次-1)` 放大；漏怪按怪物类型扣 1/1/2/2/5 点 |
| R5 | P0 | 难度曲线有梯度（见 §7.3） | 仿真三策略结果必须分别落在：不建塔→第 2 波失守；无脑铺塔→第 9–13 波失守；精选升级→通关且剩余 10–18 生命 |
| R6 | P0 | 暂停 / 倍速（1×/2×/3×）/ 重开 | 暂停时怪物、投射物、波次计时全部冻结；倍速不改变逻辑结果（同一随机种子下结果一致） |
| R7 | P0 | 移动端可玩 | 390px 宽下 5 张塔卡片不换行、不截断；画布等比缩放；点击目标有效区 ≥ 24×24 CSS px |
| R8 | P0 | 零图片资源，画面全部程序化绘制 | 仓库中不存在 .png/.jpg/.webp 游戏素材（`docs/` 截图除外）；任意 DPR 下无模糊 |
| R9 | P1 | 键盘操作 | `1–5` 选塔、`空格` 开波、`P` 暂停、`Esc`/右键取消 |
| R10 | P1 | 波次可提前开始 | 布防 12 秒倒计时；点「立即开战」立刻进入下一波 |
| R11 | 🆕 P0 | 经济闭环明确 | 起始金币 320；每清一波奖励 `20 + 波次×4` 金币；击杀按怪物赏金入账；太阳花周期性产金（见 §7.1） |
| R12 | 🆕 P0 | 胜负判定无歧义 | 仅在 `phase` 为 `build` 时允许开波；仅在场上无怪且生成队列空时判定清波；生命 ≤0 立即 `lost`；撑过第 15 波立即 `won` |
| R13 | 🆕 P1 | 索敌可预期 | 同类型塔在射程内优先攻击**沿路径推进最远**（dist 最大）的敌人，使"堵路口"策略稳定生效 |
| R14 | 🆕 P1 | 范围伤害有衰减 | 溅射/冰冻塔对范围中心全额、边缘按 `1 - 距离/半径 × 0.45` 衰减（最低 55% 伤害） |

### 4.3 明确排除（v2 候选，本期不做）

音效 / 第二张地图 / 无尽模式 / 本地存档 / 关卡选择 / 成就 / 分享成绩。

**排除理由统一为一条**：它们都在扩大产品的表面积，而 v1.0 要证明的是"一局做对"，不是"内容很多"。

## §5 游戏机制规格

### 5.1 核心循环

```
布防(build, 12s) → 开波(wave) → 生成/移动/交战 → 清波(奖励金币) → 回到布防 …
                                      ↓ 生命≤0
                                    失败(lost)
                      撑过第15波清空 → 通关(won)
```

### 5.2 状态机（✅ 已校验）

`phase` 仅有四个取值，每帧据其决定跑不跑生成与胜负判定——避免"暂停时怪物还在动"类经典 bug。

| 状态 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| `build` | 布防期 | 开局；每波清空后 | `buildTimer ≤ 0` 或玩家手动开波 |
| `wave` | 交战期 | 开波 | 生成队列空 **且** 场上无怪 |
| `won` | 通关 | 清完第 15 波 | —（终态） |
| `lost` | 失败 | 萝卜生命 ≤ 0 | —（终态） |

> ⚠️ 说明：粒子与飘字在 `won`/`lost` 下仍继续更新，避免失败瞬间画面僵住（代码 `update()` 先 `updateEffects` 再早退）。属体验细节，非状态本身。

### 5.3 经济系统（🆕 本版补全，✅ 已校验）

| 项目 | 数值 | 来源 |
|---|---|---|
| 起始金币 | **320** | `START_COINS` |
| 清波奖励 | **20 + 波次 × 4**（第 1 波=24，第 15 波=80） | `finishWave()` |
| 击杀赏金 | 见 §7.1 怪物表（9/8/16/18/130） | `killEnemy()` |
| 太阳花产金 | 每 **7** 秒产 `22 × (1 + 0.5×(等级-1))`（L1=22，L2=33，L3=44） | `stats()` + `incomeEvery` |
| 拆除返还 | 累计投入 `invested` 的 **60%**，立即到账 | `sellTower()` |

> ⚠️ 修正：原版 README/`docs/PRD.md 均写"每 7 秒"，但 `config.js` 太阳花定义处的**注释**写"每 6 秒产金币"，与字段 `incomeEvery: 7` 及实际行为不符。本文档以代码字段为准（7 秒），建议同步修正该注释。

### 5.4 升级公式（✅ 已校验，🆕 补全溅射/产金/灼烧缩放）

设塔基础值为 `base`，等级 `L`（1–3）：

- 伤害：`base × 1.65^(L-1)`（L1=base，L2≈1.65×，L3≈2.72×）
- 射程：`base + 18 × (L-1)`
- 攻击间隔：`base × 0.88^(L-1)`
- 溅射半径（仅魔法塔/冰冻塔）：`base_splash + 6 × (L-1)`（魔法 82→88→94；冰冻 58→64→70）
- 太阳花产金 / 火焰塔灼烧 DPS：`base × (1 + 0.5×(L-1))`（太阳 22→33→44；灼烧约 9→14→18）
- 升级花费（按**基础造价**计，非累计）：L1→L2 = `round(基础×0.9)`；L2→L3 = `round(基础×1.3)`

### 5.5 伤害结算顺序（🆕 本版新增，✅ 已校验）

1. **护盾优先**：护盾怪先扣盾，盾清零后剩余伤害进入护甲减伤。
2. **护甲减伤**：`applied = max(1, 剩余伤害 - 护甲)`（铁甲怪护甲 4、首领护甲 3）。
3. **灼烧无视护甲**：火焰塔持续灼烧按 `ignoreArmor` 直接结算。
4. **范围衰减**：溅射/冰冻对中心全额，边缘最低 55%（见 R14）。

### 5.6 索敌规则（🆕 本版新增，✅ 已校验）

单座塔在射程内遍历敌人，选择 `dist`（沿路径已行进距离）**最大**者——即"最靠近萝卜"的敌人优先。这保证"在路口密集建塔"能稳定拦截最先到达的威胁，是策略成立的基础。

## §7 体验决策（决策，而非视觉稿）

### 7.1 首 60 秒

目标：**不写教程**。用界面自身传达规则。

- 打开即是布防状态，12 秒后自动开波——不点任何东西也能看到游戏发生
- 塔卡在底部常驻，价格直接印在卡上，买不起时置灰
- 选中塔卡后，鼠标划过地图即显示绿色/红色可建提示与射程圈

**为什么不放教程**：教程本身就是一次「安装」。如果规则不能用界面表达，说明设计有问题，不该用文字补。

### 7.2 失败与重试

- 失败页明确给出：坚持到第几波、击杀数——**用数据代替安慰**
- 一键重开，不刷新页面、不回到首页
- 不做"看广告复活"

### 7.3 难度曲线（有仿真证据，不是感觉）（✅ 已校验）

逻辑层不依赖 DOM/Canvas，因此可无头跑完整对局。三条策略的实测结果：

| 策略 | 结果 | 结论 |
|---|---|---|
| 不建塔 | 第 2 波失守 | 失败路径可达 |
| 无脑铺塔、从不升级（纯瓶子炮） | 第 9 波失守 | 错误策略会被淘汰 |
| 少而精、先铺攻击塔再补经济与魔法塔、最后升级核心塔 | 通关，剩 11/20 生命 | 正确策略能赢，但不是躺赢 |

**这条要求的价值**：它把"难度合适"从形容词变成了断言。改动任何数值后重跑仿真，不满足 §4.2 R5 就是回归。

重制版经仿真校准（确定性，可复现）：不建塔→第 2 波失守；无脑铺塔→第 9 波失守；精选升级→通关剩 11 血、终局金币约 584——经济在后期仍被怪物强度持续收紧。

### 7.4 信息密度

场上一屏内必须同时可见：生命、金币、波次、全部 5 种塔及其价格、当前选中塔的数值。任何需要"点开二级菜单才能决策"的信息都视为设计缺陷。

## §8 技术架构（🆕 本版新增）

### 8.1 分层

```
index.html      页面骨架（无构建步骤，原生 ES Module）
styles.css      全部界面样式
js/config.js    数据层：地图、路径、塔/怪物/波次数值（不碰 DOM/Canvas）
js/game.js      逻辑层：状态机、寻路、攻击、伤害、波次、经济（纯函数 update(state, dt)）
js/render.js    渲染层：canvas 绘制地图/塔/怪/投射物/粒子
js/ui.js        适配层：canvas 尺寸(DPR)、输入映射、HUD、商店、主循环(rAF)
```

### 8.2 关键约束与取舍

- **逻辑与渲染彻底分离**：`game.js` 零 DOM/Canvas 依赖，只接受 `(state, dt)` 并返回新状态/事件。代价是渲染要自己从 state 取数；收益是可在 Node 中跑仿真与单测。✅
- **零图片资源**：全部为 canvas 基本图形组合。体积极小、任意分辨率不糊、改配色无需重导资源。✅
- **逻辑坐标固定 960×600，实际分辨率跟 DPR**：所有绘制用逻辑坐标，`setTransform` 统一缩放，一套坐标适配手机窄屏与高分屏。✅
- **波次是数据不是代码**：`WAVES` 为 `{type, count, gap, delay}[]`，调难度只改数组。✅
- **状态机而非布尔标志**：见 §5.2。✅
- **塔与图标同绘制函数**：商店图标与场上塔共用一套绘制，避免"图标与实物不符"。✅

### 8.3 性能预算（✅ 设计约束）

- 无第三方请求、无构建、无运行时依赖；
- 画面由 `requestAnimationFrame` 驱动，倍速仅改变 `dt` 累加步长，不改变逻辑结果（同种子可复现）；
- 投射物/粒子均有生命周期回收，避免数组无限增长。

## §11 成功度量

### 11.1 指标

| 编号 | 指标 | 定义 | 目标 | 测量方式 |
|---|---|---|---|---|
| M1 | 规则可理解性 | 首次玩家在无提示下完成第一次建塔的比例 | ≥ 4/5 | 人工试玩观察 |
| M2 | 单局时长 | 从开波到胜负判定 | 6–12 分钟 | 仿真 + 试玩计时 |
| M3 | 三次内通关率 | 连续 3 局内至少通关 1 次的比例 | 40–60% | 人工试玩 |
| M4 | 失败后重试率 | 失败后 30 秒内点"再来一局"的比例 | ≥ 70% | 人工试玩观察 |
| M5 | 评估者理解度 | 同行阅读 README 后能复述"逻辑与渲染分离"的价值 | 定性通过 | 访谈 |

### 11.2 在没有埋点的前提下怎么测

本产品**主动放弃**行为埋点。理由：为了拿留存数据而引入统计 SDK，会同时引入隐私声明、Cookie 同意、第三方可用性依赖——对一个十分钟小游戏，这是净负债。

替代方案：

1. **仿真替代留存指标**：难度与时长这类可被模型化的指标，用无头仿真跑，不依赖真实用户
2. **人工试玩替代转化漏斗**：5 人小样本、结构化的观察记录（是否无需提示就会建塔、卡在哪一波）
3. **仓库信号替代使用量**：star / issue 质量 / fork 后是否有改动

**明确承认代价**：无法回答"有多少人在第 7 波放弃"。接受这个盲区，因为对应的补救成本高于产品本身的价值。

### 11.3 不测什么

DAU、留存率、付费转化、分享率。原因：无账号、无埋点、无商业化——测了也没有可行动的空间。

## §12 决策记录

| 编号 | 决策 | 代价 | 收益 | 被否掉的方案 |
|---|---|---|---|---|
| D1 | 纯静态、无后端 | 无排行榜、无云存档、无法做多人 | 零运维、零成本、零隐私负担 | 加一个 Node 服务存分数 |

| D5 | 一局 15 波≈10 分钟 | 单局内容密度低于原版 | 匹配"八分钟空隙"的真实场景 | 单局 30 波 |

| D7 | 塔的视觉复用同一套绘制函数 | 商店图标与场上塔强耦合 | 图标与实体永远一致，不会出现"图标和实物不符" | 单独画图标 |
| D8 🆕 | 清波奖励随波次线性增长（`20+wave×4`） | 后期金币更宽裕，需靠怪物强度收紧 | 给玩家"撑过一波就有回报"的正反馈，且可仿真校验 | 固定奖励或仅击杀赏金 |
