## §0 摘要（一屏读完）

网页端塔防小游戏，打开即玩，无需安装/账号/内购。核心是**资源与地形的双重约束**：金币有限、好位置有限，玩家必须判断哪段路值得投资。一局 15 波、约 10 分钟。

**差异化不在于「更好玩」——塔防品类已经饱和——而在于「工程可验证」**：逻辑层与渲染层完全分离，整套玩法可在 Node 中无头跑完，难度曲线是仿真调出来的，而不是拍脑袋定的。

## §1 问题与机会

### 1.1 用户在什么时刻需要它

> 晚上十点，你在电脑前等一个构建跑完，或者开会前还有八分钟。你想玩点什么，但不想为此安装一个 300MB 的手游、注册账号、看 30 秒广告，也不想在手机上被推送打断。

这个场景的关键约束不是"想玩游戏"，而是**「短、无承诺、立刻开始」**。任何安装步骤都会让人放弃。

### 1.2 现有方案为什么不够

| 现有方案 | 具体失败点 |
|---|---|
| 原版《保卫萝卜》手游 | 需要安装；有内购与体力机制；旧版本已停止更新 |
| Flash 时代的网页塔防 | 需要模拟器；分辨率与性能不可用 |
| Steam / 主机塔防（Kingdom Rush、Bloons TD） | 品质高但需付费 + 安装，与"八分钟"场景冲突 |
| 视频攻略 | 不参与，只观看，不解决"我想玩" |
| 其他网页塔防 | 多数缺少难度校准，要么一局永远赢不了，要么十分钟通关后没有复玩动力 |

**共同缺口**：没有一个能「打开就用、十分钟打完一局、且难度经过验证」的选项。

### 1.3 为什么现在做

- 现代浏览器已具备全部所需能力（Canvas 2D、ES 模块、requestAnimationFrame），无需任何运行时依赖；
- GitHub Pages 提供零成本、零运维的静态托管；
- 作者需要一件能同时证明**玩法设计**与**工程质量**的作品。

## §2 目标

### 2.1 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 从打开链接到可以操作，不超过 2 秒（4G 中端手机） | 首屏 LCP 实测 |
| G2 | 一局完整对局 6–12 分钟，且难度曲线有梯度 | 仿真验证（§5.2）+ 人工试玩 |
| G3 | 玩法逻辑可被自动化验证，不依赖人工目测 | `game.js` 无 DOM/Canvas 依赖，可在 Node 中跑完整对局 |

### 2.2 非目标（明确不做）

- **不做多人 / 排行榜**：需要后端与账号体系，与"零运维"冲突
- **不做付费 / 广告 / 内购**：本产品不是商业项目
- **不做关卡编辑器**：面向玩家的创作工具是另一个产品
- **不做剧情 / 角色养成**：超出"十分钟一局"的容量
- **不做原生 App 打包**：网页已是完整交付形态

### 2.3 反目标（什么算失败，即使技术上跑通了）

- **A1** 玩家第一次打开，不知道"先点卡片再点地面"——技术正常运行，产品失败
- **A2** 无论怎么打都能赢，或者怎么打都赢不了——数值失衡，失去决策价值
- **A3** 手机端需要精确点击才能建塔，误触率高到让人放弃
- **A4** 为了做数据而引入埋点，使产品带上前端产品的隐私负担
- **A5** 代码只能"看"，不能"验"——无法用任何自动化手段证明玩法正确

## §3 用户与任务

### 3.1 两类用户，两种诉求

| 用户 | 真实诉求 | 成功的一刻 |
|---|---|---|
| **玩家**（顺路点进来） | 立刻玩、别教我、别让我卡住 | 三分钟内搞懂规则，一局有输有赢 |
| **评估者**（同行／招聘方） | 60 秒内判断技术水平 | 看懂"逻辑与渲染分离 + 仿真调参"这件事的分量 |

这两类用户的诉求不冲突，且可以同时满足，因此不需要分叉产品线。

### 3.2 核心任务（Jobs to be Done）

> 当我只有十分钟且不想做任何准备工作时，我想要一个能立刻开始、且真的需要动脑的小游戏，这样我能在短时间内获得一次完整的挑战与结束感。

### 3.3 为什么不做用户画像

不做年龄/职业/收入分层。产品只有一个决策依据：**这次会话有多长**。任何不能用"会话时长"解释的用户差异，对本产品的设计没有影响。

## §4 范围与需求

### 4.1 版本范围

v1.0 只做**单张地图 + 完整单局循环**。多地图、无尽模式、音效全部推后（§4.3）。

### 4.2 需求清单

优先级定义：**P0 = 缺了就不是这个产品**；P1 = 影响体验但可延后。

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| R1 | P0 | 打开即可玩，无账号、无安装、无引导弹窗 | 冷加载到可点击 ≤ 2s；首屏无任何模态框；不产生任何第三方网络请求 |
| R2 | P0 | 建塔：选卡 → 点空地 → 扣费建造 | 金币不足时按钮置灰且给出差额提示；路面/装饰格不可建造（红色高亮）；已占用格不可重复建造 |
| R3 | P0 | 塔可升 3 级、可拆除 | 升级后伤害 ×1.65、射程 +18、间隔 ×0.88；满级后按钮显示"已满级"；拆除返还投入的 60% 且立即到账 |
| R4 | P0 | 15 波怪物，20 点生命，生命归零失败 | 第 5/10/15 波为首领波；每波生命按 `1 + 0.22 × (波次-1)` 放大；漏怪按怪物类型扣 1/2/5 点 |
| R5 | P0 | 难度曲线有梯度（见 §5.2） | 仿真三策略结果必须分别落在：不建塔→第 2 波失守；无脑铺塔→第 9–13 波失守；精选升级→通关且剩余 10–18 生命 |
| R6 | P0 | 暂停 / 倍速（1×2×3×）/ 重开 | 暂停时怪物、投射物、波次计时全部冻结；倍速不改变逻辑结果（同一随机种子下结果一致） |
| R7 | P0 | 移动端可玩 | 390px 宽下 5 张塔卡片不换行、不截断；画布等比缩放；点击目标有效区 ≥ 24×24 CSS px |
| R8 | P0 | 零图片资源，画面全部程序化绘制 | 仓库中不存在 .png/.jpg/.webp 游戏素材（`docs/` 截图除外）；任意 DPR 下无模糊 |
| R9 | P1 | 键盘操作 | `1–5` 选塔、`空格` 开波、`P` 暂停、`Esc`/右键取消 |
| R10 | P1 | 波次可提前开始 | 布防 12 秒倒计时；点「立即开战」立刻进入下一波 |

### 4.3 明确排除（v2 候选，本期不做）

音效 / 第二张地图 / 无尽模式 / 本地存档 / 关卡选择 / 成就 / 分享成绩。

**排除理由统一为一条**：它们都在扩大产品的表面积，而 v1.0 要证明的是"一局做对"，不是"内容很多"。

## §5 体验决策（决策，而非视觉稿）

### 5.1 首 60 秒

目标：**不写教程**。用界面自身传达规则。

- 打开即是布防状态，12 秒后自动开波——不点任何东西也能看到游戏发生
- 塔卡在底部常驻，价格直接印在卡上，买不起时置灰
- 选中塔卡后，鼠标划过地图即显示绿色/红色可建提示与射程圈

**为什么不放教程**：教程本身就是一次「安装」。如果规则不能用界面表达，说明设计有问题，不该用文字补。

### 5.2 难度曲线（有仿真证据，不是感觉）

逻辑层不依赖 DOM/Canvas，因此可无头跑完整对局。三条策略的实测结果：

| 策略 | 结果 | 结论 |
|---|---|---|
| 不建塔 | 第 2 波失守 | 失败路径可达 |
| 无脑铺塔、从不升级 | 第 11 波失守 | 错误策略会被淘汰 |
| 少而精、先升满核心塔 | 通关，剩 16/20 生命 | 正确策略能赢，但不是躺赢 |

**这条要求的价值**：它把"难度合适"从形容词变成了断言。改动任何数值后重跑仿真，不满足 §4.2 R5 就是回归。

首次调参时仿真暴露了失衡：终局金币堆积 1086、中后期零漏怪。修正后终局金币降至 54，经济才真正收紧。

### 5.3 失败与重试

- 失败页明确给出：坚持到第几波、击杀数——**用数据代替安慰**
- 一键重开，不刷新页面、不回到首页
- 不做"看广告复活"

### 5.4 信息密度

场上一屏内必须同时可见：生命、金币、波次、全部 5 种塔及其价格、当前选中塔的数值。任何需要"点开二级菜单才能决策"的信息都视为设计缺陷。

## §6 硬约束

| 约束 | 具体值 | 原因 |
|---|---|---|
| 交付形态 | 纯静态站点，GitHub Pages 托管 | 零运维、零成本 |
| 依赖 | 0 个运行时依赖、0 个构建步骤 | 下载即运行 |
| 后端 | 无 | 无账号、无隐私风险、无成本 |
| 网络请求 | 仅自身资源，禁止第三方请求 | 隐私；也避免被第三方可用性拖垮 |
| 埋点 | **无** | 见 §7.2 |
| 逻辑坐标 | 固定 960×600，实际分辨率跟 DPR | 一套坐标同时适配手机与高分屏 |
| 无障碍 | 键盘可达；canvas 内实体对读屏不可达 | 已知缺口，见 §9 R-3 |

## §7 成功度量

### 7.1 指标

| 编号 | 指标 | 定义 | 目标 | 测量方式 |
|---|---|---|---|---|
| M1 | 规则可理解性 | 首次玩家在无提示下完成第一次建塔的比例 | ≥ 4/5 | 人工试玩观察 |
| M2 | 单局时长 | 从开波到胜负判定 | 6–12 分钟 | 仿真 + 试玩计时 |
| M3 | 三次内通关率 | 连续 3 局内至少通关 1 次的比例 | 40–60% | 人工试玩 |
| M4 | 失败后重试率 | 失败后 30 秒内点"再来一局"的比例 | ≥ 70% | 人工试玩观察 |
| M5 | 评估者理解度 | 同行阅读 README 后能复述"逻辑与渲染分离"的价值 | 定性通过 | 访谈 |

### 7.2 在没有埋点的前提下怎么测

本产品**主动放弃**行为埋点。理由：为了拿留存数据而引入统计 SDK，会同时引入隐私声明、Cookie 同意、第三方可用性依赖——对一个十分钟小游戏，这是净负债。

替代方案：

1. **仿真替代留存指标**：难度与时长这类可被模型化的指标，用无头仿真跑，不依赖真实用户
2. **人工试玩替代转化漏斗**：5 人小样本、结构化的观察记录（是否无需提示就会建塔、卡在哪一波）
3. **仓库信号替代使用量**：star / issue 质量 / fork 后是否有改动

**明确承认代价**：无法回答"有多少人在第 7 波放弃"。接受这个盲区，因为对应的补救成本高于产品本身的价值。

### 7.3 不测什么

DAU、留存率、付费转化、分享率。原因：无账号、无埋点、无商业化——测了也没有可行动的空间。

## §8 决策记录

| 编号 | 决策 | 代价 | 收益 | 被否掉的方案 |
|---|---|---|---|---|
| D1 | 纯静态、无后端 | 无排行榜、无云存档、无法做多人 | 零运维、零成本、零隐私负担 | 加一个 Node 服务存分数 |
| D2 | 逻辑层与渲染层彻底分离 | 多一层间接，渲染需自行取数 | 整套玩法可在 Node 中跑仿真 → 难度可验证 | 逻辑与绘制写在一起（更快，但只能人工目测） |
| D3 | 零图片资源 | 美术上限受 canvas 绘制能力限制 | 体积极小、任意分辨率不糊、改配色不用重导资源 | 手绘 sprite 图集 |
| D4 | 只做一张地图 | 内容量看起来薄 | 把全部精力压在"单局质量"与系统完整性上 | 做 5 张地图 |
| D5 | 一局 15 波≈10 分钟 | 单局内容密度低于原版 | 匹配"八分钟空隙"的真实场景 | 单局 30 波 |
| D6 | 不做埋点 | 无法量化留存 | 无隐私合规负担，静态站可长期零维护 | 接入统计 SDK |
| D7 | 塔的视觉复用同一套绘制函数 | 商店图标与场上塔强耦合 | 图标与实体永远一致，不会出现"图标和实物不符" | 单独画图标 |

## §9 风险与未决问题

| 编号 | 风险 / 问题 | 影响 | 应对 |
|---|---|---|---|
| R-1 | 塔防品类极度饱和，容易被判定为"又一个塔防" | 高 | 差异化锚定在"可验证的工程"而非玩法新奇；README 首屏即给出仿真结论 |
| R-2 | 数值一旦改动，§5.2 的仿真结论失效 | 中 | 计划将仿真脚本入库并纳入改动流程（见 Q-2） |
| R-3 | canvas 内容对读屏软件不可达 | 中 | v1.1 补 DOM 侧的等效状态描述（当前仅键盘可达） |
| R-4 | 小屏点击精度不足导致误操作 | 中 | R7 已约束有效区 ≥ 24px；仍建议后续做大按钮布局 |
| R-5 | 无音效，沉浸感弱 | 低 | v1.2 引入；需解决素材来源与默认静音策略 |
| Q-1 | 是否增加第二张地图以支撑"内容量"的印象？ | — | 待定。倾向不加，除非能复用同一套地图数据结构 |
| Q-2 | 仿真脚本是否作为公开资产入库？ | — | **倾向入库**。当前脚本仅在本地，README 声称"经仿真调参"但仓库内无法复现——这是文档与仓库的不一致，应修 |
| Q-3 | 是否提供本地存档？ | — | 待定。会削弱"十分钟一次性体验"的定位，需先验证是否有人真的想接着打 |
